One foundation, so separate apps work as one system

Fall Kit core is a small set of modules every app in the estate runs. With it, apps that were built apart can work together safely. Each one signs everything it says in one format (LIGHT, the estate's own compact message format) and checks everything it hears before reading a byte of it. When one app refuses an attack, every other app learns from it. Each keeps its memory in one checked file, cannot spend past the budget it was given, and records the useful work other apps do for it.

Two of the estate's real apps run on it today: break-it, a gateway that checks every incoming packet of data before any software reads it, and konomi-slm, a library of tested patterns that answers with a receipt you can check, or says it does not know.

If you build an app

  1. From a clone of fall-kit, run node core/tools/vendor-into.mjs <your repo>. It copies the foundation's files (not its tests, tools or page) into vendor/fall-kit-core/, byte for byte from the committed blobs, and pins them in FALL-KIT-CORE.json. vendor/SOURCES.json inside it pins every kernel to the commit it came from.
  2. Give your app an identity and a node, with the skills it offers:
import { makeIdentity } from './vendor/fall-kit-core/identity.mjs';
import { createNode } from './vendor/fall-kit-core/node.mjs';

const node = await createNode({
  name: 'my-app',
  identity: await makeIdentity(),           // an Ed25519 key, made by WebCrypto
  budget: 1000,                             // asks it may make, never more
  skills: { triage: async (input) => ({ verdict: 'VERIFIED', receipt: { /* … */ } }) },
});

An answer is VERIFIED with a receipt, or ABSTAIN. By default the asker checks a receipt by re-hashing it: give it a receiptHash, the SHA-256 of JSON.stringify of its other fields, or pass your own check for the skill in checks. A receipt that does not re-hash counts as a failed answer and halves the coupling.

  1. Pin the peers you trust, out of band: await node.pin(theirCard). A card proves its key and nothing more. Whether to trust the key is your decision.
  2. Carry bytes between nodes over any channel you like. node.ask(skill, input) returns the packet to send and which peer it is for ({ bytes, to }); node.hear(bytes) returns the verdict and any replies to carry back ({ replies: [{ to, bytes }] }). The node never opens a connection itself.

How it works

A node is one identity carrying six things at once. Everything it says is a signed LIGHT packet. Everything it hears passes the LIGHT door, stage by stage on the raw bytes, before one byte of the body is decoded.

One ask, step by step, from the real run

  1. The budget first. break-it's wallet authorises the ask before any packet exists, and signs a token that names the ask. A node with a budget of five could make five asks; the sixth was refused and no packet was built for it.
  2. A signed LIGHT packet. The ask, its input and the token go into one packet: the LIGHT codec's bytes, an Ed25519 signature, a counter, and the recipient's key inside the signed body. The run carried … packets, about … bytes each.
  3. The door. konomi-slm checks size, magic, version, length, dictionary, sender, signature and counter on the raw bytes. Only then does it decode the body, then check that the message is addressed to it.
  4. The skill answers. konomi-slm answers from its triage pattern alone. It returns VERIFIED with its own receipt, or ABSTAIN when no verified pattern covers the input.
  5. The proof is checked. break-it re-hashes the receipt. If it checks, the coupling to konomi-slm grows (500,000 to 625,000 parts of a million on the first one). If it does not, the coupling halves, so the asks go elsewhere. After the run, the honest coupling stood at … and the dishonest one at ….
  6. The work is recorded. break-it signs one value record for each verified answer it used. konomi-slm, sent that ledger, records only the values for answers it really gave. Both ledgers then give the same credits.

Shared immunity

A peer cannot make a node refuse a packet the node's own door would admit. Every antigen is re-run on the receiver's door, and adopted only when that door refuses it at a stage that can never become valid. In the run, … antigens were adopted and the same attack was then … at the receiver. The valid packet hidden in a bundle was ….

    Security and data protection, answered straight

    • Where does data go? Nowhere the modules send it. They open no connections. You carry the bytes between your own systems, over your own channel.
    • Keys. Each node has one Ed25519 key, made by WebCrypto. The wallet signs its budget tokens with the private key in text form, so that form sits in the node's memory: a node's key is as safe as the process it runs in. A peer is trusted only when you pin its card. If a key leaks, pin a new one and drop the old.
    • Forgery, tampering, replay, misdirection. Each is refused before any parser runs. The run's six hostile packets were all refused, none decoded, none admitted. A packet replayed to a node it was not addressed to is refused by name.
    • Poisoned learning. A shared antibody is adopted only after the node's own door refuses the same bytes. A valid packet slipped into a bundle is blocked, never learned.
    • Not covered. A stolen key, a host that is already compromised, and content that is harmful once read: LIGHT carries data faithfully, so the screen that shows it must still escape it. A dishonest peer can cost you one answer before its coupling halves. Receipts are tamper-evident: the asker re-hashes them; it does not recompute the answer.

    Risks, answered

    • "It is one machine today." True. Phase 1 proves the cells on one machine, in one process and in separate processes. Meshing across devices is the next phase, and it will have its own sealed claims.
    • "A pattern library can be wrong." konomi-slm abstains when no verified pattern covers an input, and every answer carries the held-out score of the pattern behind it. The foundation records which answers were used, so a wrong one can be traced.
    • "Another dependency." There are none at runtime. These are plain modules, copied into your repo and pinned, with the gate's results committed.

    The paper: why one foundation

    The problem. Every app that has to work with another builds the same things again: a way to talk, a way to trust, a way to stop replays, a way to keep records, a way to learn from attacks. Each version is slightly different, so apps cannot safely rely on each other. The usual answer is a central broker that sees and controls everything, which is one more thing to trust, rent and defend.

    The design. Put those things in one small foundation that every app imports unchanged, and let apps exchange only bytes. Four choices carry the weight:

    • Verify before parse. The LIGHT door decides on raw bytes, in a fixed order, and decodes a body only after the signature and the counter pass. Bytes in any other format fail at the magic number. Bytes from a key nobody pinned fail at the sender or the signature. The decoder is never called for either.
    • Negative selection. A refusal becomes an antibody, and antibodies travel. The receiver adopts one only if its own door refuses the same bytes at a stage that can never become valid. So shared learning can only make a node stricter about what it would already refuse.
    • Capabilities with budgets. A node's identity is also a wallet with a finite budget. An ask is authorised, and its token signed, before the packet exists. A node cannot exceed what it was given by construction, not by policy.
    • Evidence, not reputation. A coupling grows only when an answer's proof checks, and halves when it does not. Contributions are recorded only where the recording node can re-check them, so the ledger counts work, not claims of work.

    What is measured. Nine claims were committed before the code. Each has one rule over measured facts, applied by a pure judge, and CI re-runs the whole measurement and demands the receipt byte for byte. The two apps are real estate apps, run from their own repos, not test doubles.

    Honest limits. One machine, for now. Recall is by resemblance of words (character n-grams), not by meaning in a deep sense. The cost case uses break-it's measured rate unless you run the proof here; then it uses yours. The foundation keeps its promises only as far as its keys are kept.

    What comes next. LIGHT for every store and channel in the estate; the mesh across devices; living websites whose front door is a model in the visitor's own browser above this same verify-first door; and the contribution record running everywhere, its switch off until a human decides with counsel. Each will get its own sealed claims, one phase at a time.

    Questions

    What is the shared foundation?

    A small set of JavaScript modules every app in the estate runs, so the apps can work together safely: they speak one signed format (LIGHT), check each other before reading anything, share what they learn about attacks, keep their memory in one checked file, cannot spend past a budget, and record the useful work other apps do for them.

    Does it send my data anywhere?

    No. The modules make no network calls of their own. Apps hand each other bytes over whatever channel you choose, and on this page everything happens inside your browser tab.

    What does it not protect against?

    A stolen private key, a machine that is already compromised, and data that is harmful once read (LIGHT carries data faithfully; the app that shows it must still escape it). A dishonest peer can waste one answer before its coupling halves. Today it runs on one machine; meshing across devices is the next phase.

    How do I know the claims are true?

    Nine claims were committed before any of the code existed. A pure judge turns the measured facts into verdicts, CI re-runs the measurement on every push and demands the same receipt byte for byte, and this page re-runs it in your browser from the two apps' own live sites.

    What does it cost?

    It is MIT-licensed, with no licence fee. It runs on machines you already have. The cost case on this page compares that with sending the same traffic through a managed API gateway and web application firewall, at dated public list prices.
