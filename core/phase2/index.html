Phase 2 of the estate going live · fifteen claims sealed before the code

One language inside, and one checked edge to the outside

LIGHT is the estate's own compact message format. A LIGHT packet carries who sent it, a counter so it can never be replayed, and a signature, and the door checks all of that on the raw bytes before it reads a single byte of the body. Phase 2 makes LIGHT the language every part of the estate keeps and carries things in. The outside still speaks JSON and the web, so one thin edge takes those in, checks them against a declared shape, and re-says them inside as signed packets.

The point is that nothing inside ever parses bytes it cannot trust. Bytes in any other format stop at the first four. Bytes in LIGHT's own format that no trusted key signed stop at the sender or the signature. Everything a trusted key does sign gets through, intact.

If you want to see it work

  1. Throw anything at the door. Paste text, JSON, a web request, anything, or pick an example. Press Hear it: the door says exactly where it stopped it, and that it never decoded the body.
  2. Make a real packet. Press Sign it as a packet: the same text, signed with a public test key the door has pinned. It is admitted. Then press Change one byte (refused at the signature) and Send it again (refused at the counter).
  3. Go through the edge. Give the edge an example of what it should accept, then a request. A request that fits becomes a signed packet inside and comes back out as the same JSON; one that does not is refused at a named stage and no packet is built.
  4. Read the receipt. The measured claims below are re-judged in your tab from the receipt's own facts.

If you build an app

The edge is one module in the shared foundation (core/edge.mjs). Copy the foundation into your repo with node core/tools/vendor-into.mjs <your repo>, then:

import { sealInside, outbound, shapeOf } from './vendor/fall-kit-core/edge.mjs';

// declare what this edge accepts (or write the shape by hand: string, int, list, object, any…)
const shape = shapeOf({ customer: 'ACME', amount: 12, lines: [{ sku: 'X1', qty: 1 }] });

// outside → inside: checked (size, UTF-8, JSON, shape), then signed by the edge's own key
const inn = await sealInside(requestBytes, { shape, sender: edge.slot, counter }, edge.sign);
if (!inn.ok) return reply(400, inn.stage + ': ' + inn.why);          // no packet was built
node.hear(inn.bytes);                                                  // inside, only signed LIGHT

// inside → outside: through the door first, then standard JSON
const out = await outbound(packetBytes, { peers, verifyBytes, lastCounter });
if (out.ok) reply(200, out.json);

How it works

  1. The edge is the only place outside formats are read. A request is checked in a fixed order: its size, whether it is valid UTF-8, whether it parses as JSON, and whether it fits the shape the edge declared it would take. Only then is the value re-said as a LIGHT packet, signed by the edge's own key. A request refused at any step builds no packet.
  2. The door decides on raw bytes. Every packet inside, from the edge or from another part, passes the same stages before its body is decoded: size, the four-byte magic LGT1, the version, the length, the dictionary, a sender with a pinned key, a signature that verifies, and a counter that has not been used.
  3. Learning makes it stricter, never blind. Each refusal is remembered as an antibody. The measurement checks that after learning from every refused payload, the node still admits everything its trusted peer signs.
  4. Going out, the door comes first. A packet leaves as JSON only if it passes the door. A forged or replayed packet produces no output at all.

    Security and data protection, answered straight

    • What it stops. Bytes in any format other than LIGHT, at the first four bytes. LIGHT-shaped bytes that no pinned key signed, at the sender or the signature. A signed packet changed after signing, at the signature. A packet sent twice, at the counter. A request the edge was not declared to take, at the shape, before any packet exists.
    • What it does not stop. Content that is harmful once read, carried inside a packet a trusted key signed: it is decoded faithfully, and the part that shows or acts on it must still judge it. A stolen key. A machine already compromised.
    • Where data goes. Nowhere the modules send it: they open no connections. You carry the bytes over your own channel. On this page, everything stays in your tab.
    • Personal data. The edge declares exactly which fields it takes, so a field nobody declared is refused rather than stored. That makes data minimisation (UK GDPR and GDPR) a line of code you can read.

    Rolling it out

    1. Put the edge in front of one service you already run. Declare the shapes it takes from real examples, and watch what it refuses.
    2. Move that service's inside traffic to LIGHT, one part at a time; the edge keeps taking the old format while you do.
    3. Then the next service, with its own declared shapes. Each move is measured before the next.

    Risks, answered

    • "Most of this is refused at four bytes, so of course it holds." Yes: that is the design, and it is still worth measuring on real bytes. The harder claims are G2 and G3: LIGHT-shaped packets without a trusted signature never pass, and a node that has learned from thousands of refusals still admits everything its trusted peer signs.
    • "Is LIGHT always smaller?" No. On Kar's real journals it is far smaller than gzip, about half on a 10,000-event journal. On a journal of a few events it is a few bytes larger, because every vault carries a 32-byte SHA-256 of its contents and a header. That is why M2, "no larger on every journal", is on the receipt as measured, whichever way it went.
    • "An exact shape is strict." It is meant to be. shapeOf declares an example's exact shape; a real edge usually writes a looser one by hand (a list of up to N, text up to N characters, any JSON within a depth).
    • "Phase 2 is not finished." True, and the page says so: the passes table shows which organs have moved. Each pass is measured before the next begins.

    The organisation stops parsing untrusted input everywhere and starts parsing it in one place, with a declared shape, in front of a door that reads nothing a trusted key did not sign. Every claim behind that is re-run by a machine anyone can watch.

    The paper: one language inside

    The problem. Most breaches start with a parser: some part of a system reads bytes it should not have trusted, in a format rich enough to hide something. Every service that accepts JSON, HTML, form bodies or its own wire format is another parser, and each is written a little differently.

    The design. Give the inside of the estate one format, LIGHT, and one door that decides on raw bytes before anything is parsed: the magic number, the version, the length, the dictionary, a pinned sender, a verified signature and a fresh counter, then the body. Put the outside's formats behind one thin edge that checks size, encoding, syntax and a declared shape, and only then re-says the value inside, signed. Outbound, reverse it: the door first, then JSON.

    What is measured. Fifteen claims were committed before any of Phase 2's code, across five passes. The first pass throws the estate's own files at the door, every one whole and cut four ways, with web requests, form bodies and random bytes. It then throws six kinds of LIGHT-shaped packet that no trusted key signed, and checks that everything a trusted key signs still gets through, intact, after the node has learned from every refusal. A pure judge turns the facts into verdicts, and CI re-runs the measurement and demands the same receipt byte for byte.

    Honest limits. The signature and counter are the floor; the format is the surface reduction. Neither judges content a trusted key signed. LIGHT here is the estate's wire codec (konomi-tongue's LIGHT); falllight is a separate vocabulary for how nodes connect, not this codec. The cards and the contribution records move to LIGHT in their own phases and sessions, not here.

    Questions

    What is LIGHT?

    The estate's own compact message format: a lossless coder, a signed packet, and a door every packet passes before it is read. A packet carries who sent it, a counter so it cannot be replayed, and an Ed25519 signature; the door checks all of that on the raw bytes before decoding a single byte of the body.

    What does 'LIGHT everywhere' change?

    The estate's parts keep and carry what they know as signed LIGHT, so there is one format to check, one door, and no part that parses untrusted bytes. The outside world still speaks JSON and the web, so one thin edge takes those in, checks them against a declared shape, and re-says them inside as signed packets.

    Does LIGHT stop harmful content?

    No, and it does not claim to. The signature and the counter keep out bytes that no trusted key signed. Content carried inside a packet a trusted key did sign is decoded faithfully, and the part that uses it must still judge it. A stolen key and a compromised machine are outside what it protects.

    How was it measured?

    Fifteen claims were committed before any Phase 2 code existed. The first six were measured on a corpus pinned to five public repositories: every file, cut four ways, plus web requests to every live estate page, form bodies and random bytes. A pure judge turns the facts into verdicts, and CI re-runs the whole measurement and demands the same receipt byte for byte.
