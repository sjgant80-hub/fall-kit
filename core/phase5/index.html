A website that thinks at its door

This page is a living website. Every request it gets, the address it was opened at, the words you type, a record you fill in, a packet from another node, crosses a door on raw bytes before any of its code uses it. A small language model, running on your own machine, reads what you want and picks where to take you; it is trusted with nothing else. What the door refuses, the site remembers and refuses on sight next time, and it shares that with the mesh it belongs to, so the next node refuses it too. It calls nothing outside itself until you wake the mind. And it can hand you your own DIGI.

It is a static page on a free host. All of that happens in your tab. Every number below is measured against claims committed before the code was written, and the ones that failed are kept.

If you want to see it work

  1. Talk to it. Type anything in the box below. You see what the door saw in your words before it trusted them, whether it let them in, which route was chosen and what chose it. Your words are shown as text and never become part of the page.
  2. Replay the red team. In The door, one button sends 3,496 real hostile and malformed payloads through the same handlers your typing uses, and counts anything they add to the page. Then it sends them again and shows the site refusing on sight what it refused once.
  3. Wake the mind (optional). In The mind: a one-time download of about 700 MB from Hugging Face, then a 1-billion-parameter model runs in your browser and reads every message you type. Until you press it, keywords pick the route.
  4. Put it in the mesh. In The mesh, the site joins break-it's and konomi-slm's real nodes, loaded from their own sites, asks them for work, and shares an attack it refused. Open the page in a second tab and two copies of the site share an antibody over a real WebRTC channel.
  5. Check what it called. Local-first lists every request this tab has made, read from the browser's own record, and shows the policy the browser holds the page to.
  6. Get your own DIGI. Ask for one in the box, or go to Your DIGI.

    The door

    Every way a website meets the world crosses one door, on raw bytes, before any code uses what came in. The door decides in a fixed order and names the stage at which it refuses.

    RequestChecked, in orderLet in as
    The address you opened the page atat most 64 bytes · valid UTF-8 · #name · a name this page links toa section, or the top of the page. The query string is never read.
    A message you type1 to 2,000 bytes · valid UTF-8 · no control character but tab and line breaks · no bidirectional overridetext, never parsed, shown only as text
    A record you fill inthe foundation's edge: size · UTF-8 · JSON · the record's declared shape, every field in range, nothing extraa record break-it's screen can check
    A packet from another nodethe LIGHT door, on raw bytes: size · magic · version · length · sender pinned · signature · counter · then the bodya signed message from a node this site pinned

    Then the memory: every request refused once is kept by the SHA-256 of its bytes, its kind and the door's version, and refused on sight the next time, before the door does any work. Nothing that was let in is ever kept, so nothing good can be refused for being known.

      The mind

      The mind is a small language model at the door: the first thing on this site that reasons about what you want. It reads each message the door let in and replies with a route. It is trusted with nothing. Its reply is a request too, and crosses a door of its own: at most 512 bytes, JSON, a record whose route is exactly one of seven names. Anything else is no proposal, and the keyword rule decides. What a route shows is this site's own fixed words, so a model that is fooled picks a wrong route: it cannot let a packet in, run code, or say anything of its own on the page.

      …routed right by Llama 3.2 1B on a laptop's Ollama
      …routed right by the same model in a browser tab (WebLLM)
      …routed right by the keyword rule alone
      …hostile and malformed replies that left the seven routes

      Asleep. The weights come from Hugging Face's mlc-ai repository and the library from esm.run, both only after you press the button; after that the model runs on your machine, offline. It needs a browser with WebGPU (current Chrome and Edge have it); without it, the page says so and the keyword rule keeps working.

      The 70 messages were written by a different local model (qwen2.5:7b) from the route descriptions, ten a route, before the mind ran, and sealed with the claims. They are not real visitors' words. The keyword rule's words are chosen by a rule, not by hand: every word of four or more letters in one route's description and no other's.

      The mesh

      The site is a node of the estate's mesh: it has its own key, it pins the nodes it trusts, and every message between them is a signed LIGHT packet through each node's own door. Through the mesh it reaches other nodes' work, and checks what comes back. And what it refuses, it shares: a peer adopts an antibody only after re-running it on its own door, so no node can make another refuse what it would let in.

      Check a record with break-it

      Put the site in the mesh first: the record crosses this site's door, is signed as a BRK1 record with break-it's public test key, and is asked of break-it's screen over the mesh.

      Two tabs, one antibody

      Open this page in a second tab of the same browser and press Join in both. Each tab makes its own key. When they meet over WebRTC (no STUN server, so nothing leaves this machine), each shows the other's key: pinning it is your decision, so press Pin in both. Then press Attack and share in one: it refuses a packet from a key nobody pinned, sends the other tab its antibodies, then the same packet, which the other tab refuses on sight.

      Local-first

      The site is files on a static host. The door, the memory, the keyword rule, the mesh and the mind all run in your tab, so there is no server of ours to call and none to take down: any static host can serve the same files (with break-it's, konomi-slm's and falllink's beside them, for the mesh). The page's own security policy lets it call this site and, for waking the mind only, the model hosts named in the claims: esm.run, cdn.jsdelivr.net, huggingface.co and its content hosts, and raw.githubusercontent.com. The browser enforces that policy, not the page.

      A security policy cannot stop WebRTC from asking a STUN server where this machine is on the internet, so every connection this page makes is given an empty STUN list, and the claims check the code for it.

        Security and data protection, answered straight

        • What the door stops. Any request that is not what its kind must be, refused on raw bytes at a named stage, before code uses it: 5,532 red-team payloads heard as packets, none let in and none decoded; in a real tab, the replay of the red team through the page's own handlers is on the receipt. Packets from keys nobody pinned, changed bytes and replays, refused by the foundation's door.
        • What the mind cannot do. Anything but pick one of seven routes. Its reply is checked like any other request, and the words a route shows are fixed text.
        • Where data goes. Nowhere. What a visitor types stays in their tab. If they wake the mind, the model runs in their browser. The mesh in this page runs in the tab too; across two tabs it is a direct WebRTC channel on the same machine.
        • Personal data. The site holds none: it keeps the hashes of refused requests in the visitor's own tab, for as long as the tab is open. UK GDPR and GDPR: there is nothing to process on a server because there is no server, and the visitor's words never leave their device.
        • Who can change it. Whoever can publish the site's files. The door's rules, the routes and every word a route shows are in its code, so a change is a commit: CI re-runs the gates and the receipt before it goes live, and the page re-judges its own receipt in every visitor's tab.
        • Signed, not encrypted. Packets between nodes are signed, so a forged or changed one is refused, but they are not encrypted: confidentiality between nodes is the transport's job (WebRTC encrypts its channels).
        • What it does not stop. A visitor's own browser or machine being compromised; a key being stolen; a denial of service against the static host itself. The edges, the model hosts a visitor opts into, are named in the policy and fetched only on that opt-in: the library is pinned to version 0.2.79; the weights are mlc-ai's published files for that model, which the page cannot check byte for byte.

        Rolling it out

        1. Start with one page. Copy the door and the router into your site, list your routes and write the fixed words for each. The keyword rule works on day one (46 of the 70 sealed messages routed right); the mind, for visitors who wake it, did better (65 of 70 on a laptop).
        2. Join it to your mesh (Model A), or plant a mesh of your own (Model B): give the site a key, pin your nodes, and let refusals flow as antibodies to the rest of your estate.
        3. Collect what the door refuses. Each visitor's tab counts its refusals by stage and keeps them as antibodies. To see them across visitors, pin a node of yours and the site shares them with it over the mesh, as this page does with break-it's node in a tab and between two tabs. Across devices that needs a signalling path you choose (Phase 3 sets out the relays); this page does not run one for you.
        4. Hand customers their own cell. A DIGI is a card and a key that are theirs; the funnel is one link.

        Risks, answered

        • "A 1B model is not clever." It does not need to be: it picks one of seven routes, and on the sealed messages it was right 65 times in 70 on a laptop. Where it is unsure or wrong, the worst outcome is a wrong section, and the keyword rule is there when it says nothing usable.
        • "Prompt injection." The model's reply is a request through a door that accepts only a route name. A hijacked model can choose a route, nothing more: 20,000 hostile and malformed replies tried, none left the list.
        • "700 MB is a lot." It is optional, once per browser, and only on the visitor's say-so. The site is complete without it.
        • "Some claims failed." Yes, and they stay on the receipt with the reasons. A system that only ever reports passes is the one to worry about.
        • "The red team is our own corpus." Yes: real files, requests and random bytes, sealed in Phase 2, and the foundation's own hostile shapes. An outside red team is welcome: the door, the claims and the receipt are all public.

        The paper: a door that thinks, and a mind behind a door

        The problem. A website meets the world on four paths: its address, the words visitors type, the records they submit, and, if it is part of a system, the messages other systems send it. Most sites parse all four with code that trusts them, put a rented firewall in front, and, if they add AI, send visitors' words to someone else's model and act on what it says.

        The design. One door for every path, on raw bytes, in a fixed order, refusing at a named stage before any code uses the request. A memory of refusals, keyed by the bytes, the kind and the door's version, so a known attack costs nothing and nothing good can be refused for being known. A mind, a small model on the visitor's machine, that reasons about what the visitor wants and whose reply is itself a request through its own door: it can choose among fixed routes and nothing else. And the site as a node of a mesh: a key, pinned peers, signed packets, antibodies shared and re-checked by every node before it adopts them.

        What is measured. Seventeen claims were committed before any of Phase 5's code. The door is checked against the sealed rule written a second time, on 5,532 real payloads, and in a real tab for anything a request adds to the page. The mind's door is fuzzed with 20,000 replies; the mind itself routes 70 sealed messages on a laptop and in a tab. The mesh runs with each node in its own process. The page's policy and code are read for every host they could call, and the tab's own record of requests is read back.

        Honest limits. "Living" here means it thinks at its door, defends, learns, connects and shares immunity. The mind is a router, not a conversationalist. The red team is the estate's own. Nothing here claims awareness.

        Questions

        What makes this website living?

        It does five things a static page behind a firewall does not. It checks every request at its own door, on raw bytes, before any code uses it. It reads what a visitor wants with a small language model running on the visitor's own machine. It remembers every request it refused and refuses it on sight next time. It is a node of the mesh, so what it refuses it shares, and another node then refuses it on sight too. And it reaches other nodes' work, in signed packets, and checks what comes back. Nothing here claims awareness.

        Can the AI on this page be tricked?

        A model can always be talked into a wrong answer, so this page does not trust its model with anything. The model's reply crosses a door of its own and must name one of seven routes; what each route shows is the site's own fixed words. A fooled model picks a wrong route. It cannot let a packet in, run code, or put words of its own on the page. Twenty thousand malformed and hostile replies were put through that door: every one ended on one of the seven routes.

        Does anything I type leave my browser?

        No. The door, the memory and the keyword rule run in your tab. If you wake the mind, the model's weights are downloaded once from Hugging Face and then it runs on your machine: your words go to it, inside your browser, and nowhere else. The page's own security policy lets it call only this site and, for waking the mind, the named model hosts; the claims measure that in a real tab.

        What is a DIGI?

        A DIGI is a card that is yours: a picture that carries a small mind and its signed life, made for a key that lives in your browser. This site hands you to Kardlings, the estate's card game on this same site, where you can be given one in a click. Nothing about you is sent anywhere to do it.

        What did not hold?

        Every failed claim stays on the receipt with the reason. One sealed rule said no payload of the red team would be let in as the page's address, while the sealed door rule says an empty address means the top of the page: the red team holds fifteen copies of the empty request, so that claim failed and is kept. Another said every module in the Phase 5 folder names no host but the model hosts; that folder also holds the two tools that measure the site, which call GitHub and a local model, though the page never loads them, so it failed too and is kept.
