Every node keeps its own books

When one node of the mesh uses another's work, and the work checks, it writes that down: a signed entry in a contribution ledger, naming the work, the node that did it, and the evidence it rests on. Every node does this for itself. An auditor then takes every node's ledger into one set of books, and takes nothing on trust: it finds, for each entry, the signed answer it was for and checks it again. The books re-derive from nothing, in any browser, to the same final hash.

These books are not financial accounts. They are a record of work done and used: which node answered which question, for whom, and the evidence that the answer checked.

From the books, anyone can compute a sandbox allocation: how a pool of contribution units would be shared among the contributors, exactly, to the unit. No allocation is live. The switch is off, and only a key named when the ledger began could ever turn it on. Contribution units are not money.

    How it works

    1. Work is recorded where it is used. When a node asks another for an answer and the answer's receipt checks, the asker signs a value entry: the job, the node that answered, one contribution unit, and the digest of the answer. That is the foundation's node, unchanged since Phase 1.
    2. Only named measurers, only once. The ledger takes a value only from a measurer its first entry names, only on a node it has recorded, and only once for each job. A dishonest peer whose receipts do not check is valued by no one.
    3. The auditor trusts nothing. Each node sends its ledger as a signed LIGHT packet. The auditor admits it through the foundation's edge, replays it, and merges it into its books under a gate that finds, for every value, the holder's own signed answer packet for that job and checks its signature, its digest and its receipt (a door answer by running the door again).
    4. Leave-one-out. Phase 4 grew specialists and its gate measured what each added on rows it never saw. The founder records each as a contribution, one unit for each thousandth of balanced accuracy gained, under a gate that re-reads Phase 4's committed receipt. A value one unit off is refused.
    5. The books re-derive. Replayed from nothing, entry by entry, the books reach the same final hash and the same credits. They are kept as a LIGHT vault too, and CI rebuilds both byte for byte.
    6. A sandbox allocation, exact. The credits share a pool in whole units: floors first, then the leftover units one each to the largest remainders. A second implementation, written separately, must give the same parts.
    7. The switch is off. A live allocation needs a switch entry that only an activator named at the ledger's start can sign. These books hold none.

    How long it takes: in CI, the whole run (four nodes at work, the auditor's books, both paths) takes about half a minute; replaying the books in a browser takes under a second. They are re-derived on every push by CI, and by anyone, whenever they like, with the button above.

    The switch, and the two paths

    No allocation is live, and the ledger refuses one: …

    What turning it on would take: one entry, signed by an activator the ledger's first entry names, saying which path (the fork or the network), the size of the pool, and the digest of the legal advice it was made under. The ledger takes one switch, once, and from no other key.

    Turning it on is a decision for people, with legal advice, not something the code does. The code only makes sure that when someone does decide, it can be done one of two ways, and that nobody else can do it. Both are shown below on copies of the books, made with the demo founder's public key, and thrown away: the books on this page stay off.

    PathWhat happensMeasured on a copy
    The forkThe estate switches its own books: the activator its genesis names signs a switch for a pool, and the live allocation is the one anyone could already compute in the sandbox.…
    The networkThe books merge into a larger network that began from the same genesis: every entry is counted once, anything that clashes is refused and named, and the network's switch shares a pool across both.…

    What the network path found. The mock network already held a release of the living site's name by another key. Names here are derived from a node's key but not bound to it, so the first to record a name holds it. The merge refused the living site's own release, and, because the auditor's gate credits a value only to the key that gave the answer, it refused every value that would otherwise have been credited to the key that took the name: eleven entries in all. The living site therefore has no part in the network's allocation. The books are right to refuse, and the sealed claim, which expected one refusal, is kept as failed. Before joining a larger network, a node's name must be bound to its key. That is now done, and measured: the fix, below.

    The fix: a node's name, bound to its key

    What the network path found is fixed, and the fix was measured the way everything else here is: nine more claims and nine attacks, sealed before a line of it was written. It is called Phase 6b.

    A node's name is node: and the first 16 hex digits of its own key. Each node's own door, and the auditor's, already refused a release of a node's name by another key; the larger network's door did not, and a ledger keeps the first release of a name, whoever signed it. One rule now holds at every door that records a node, the network's included: a node is recorded only under its own key's name, and a name in the node: space is carried only by its own node's release. The rule sits in front of each door's existing check, so it can only refuse more, never let more in. And the books will not merge into a ledger that does not hold the rule: they refuse before they write anything into it.

      Security and data protection, answered straight

      • What it stops. Values from keys the ledger does not name; a second value on the same job; a value on an answer whose receipt does not check; a value one unit off what was measured; a release of a node's name by any key but its own; credit to a key that took another node's name; a live allocation without the switch; a switch from anyone but a named activator; a second switch.
      • What it does not stop. A named measurer that lies about work it really did check (its own key is its word); a stolen activator key; a policy that weighs the bases unfairly (the policy is the owner's to set, before the first entry).
      • Where data goes. The books hold keys, job names, digests and units, not people's data. Each node keeps its own ledger; the auditor's books are files anyone can read and replay.
      • A sandbox allocation is arithmetic, not an entitlement. It shows how a pool would divide under the sealed policy if someone ever decided to divide one. Nobody is owed anything by it, and the books record work, not claims on anything.
      • The demo keys are public. Every key here, the activator's included, comes from a published test seed, so anyone can make entries these books would accept. A real ledger names keys its owners hold.

      Rolling it out

      1. Write the policy first: who may measure, who may activate, how the bases weigh, the early weight. It is sealed in the first entry, before anything it weighs.
      2. Let the nodes record as they work. Nothing to add: the foundation's nodes already write their own entries. A system that is not yet a node joins by running the foundation's node beside it, as break-it and konomi-slm do (Phase 1).
      3. Run the auditor's books on a schedule, and publish them with their evidence, so anyone can re-derive them.
      4. Bind every node's name to its key before joining a larger network, so nobody can take a name first. The foundation now holds that rule at every door, and the books will not merge into a network that does not hold it.
      5. Keep the switch off until the board decides, with advice, what an allocation would mean.

      Risks, answered

      • "This is a ledger of something valuable." It is a ledger of measured work, in contribution units, which are not money. No allocation is live, and none can be without a signed switch.
      • "A node could inflate its own record." Its own ledger is only its word; the auditor's books take a value only with the signed answer behind it, checked again.
      • "The weighting is arbitrary." It is a policy, and it is the owner's: sealed at the start, published, the same for every entry.
      • "A claim failed." Yes, and it stays on the receipt: the network path refused more than it was predicted to, because a name had been taken. That finding is the reason names must be bound before a merge, and the fix that binds them is measured on this page; the failed claim stays.

      The case for the board

      The organisation gets a record of contribution that nobody has to keep, that nobody can quietly edit, and that anyone can re-derive. It commits to nothing: the switch is off, and the decision to give the record any meaning stays with the board.

      The paper: books that keep themselves

      The problem. When work flows between systems, teams and partners, who contributed what is reconstructed after the fact, by hand, from logs nobody signed, and argued over.

      The design. Record contribution where work is used: the system that relied on an answer, and checked it, signs the record. Name in advance who may measure and who may activate. Merge every record into books under a gate that re-checks the evidence. Keep the books as a hash chain anyone can replay, and compute allocations exactly, in a sandbox, until people decide otherwise.

      What is measured. Eleven claims were committed before any of Phase 6's code: that every node records its own work, that the auditor's books take every entry once and re-check every value, that they re-derive, that leave-one-out credit matches Phase 4's receipt, that the sandbox allocation is exact, that the switch is off, that both paths work on copies, that the kernel never throws, that the page and code carry none of a sealed list of words, and that a browser re-derives the books.

      The fix. The network path showed that a name derived from a key is not yet bound to it. Nine more claims and nine attacks were sealed before the fix was written: one rule at every door, that a node is recorded only under its own key's name; a refusal to merge into a ledger without the rule; Phase 6's failure reproduced exactly without it, as the control; and Phase 6 re-derived byte for byte after it.

      Honest limits. The keys are public test seeds. The larger network is a mock of the same schema; the real network's schema is not in hand. How the bases weigh is a demo policy. Contribution units are not money.

      Words used here

      • Contribution unit: the ledger's count of measured work. One unit for each verified answer a node used, here; one for each thousandth of balanced accuracy a specialist added. Not money, and not a claim on anything.
      • Credit: the units an entry gives a contributor under the policy (the maker's tenth, the owner's rest, the early weight).
      • Name: a node's name in the books, node: and the first 16 hex digits of its key. Under the rule, only that key can release it.
      • Key: an Ed25519 public key. Every node, measurer and activator is one; every entry is signed by one.
      • Job: the name of one ask and its answer, so a piece of work is valued once.
      • Signed answer: the LIGHT packet a node sent back, signed with its own key; the auditor checks the signature, that the value names exactly that answer, and the answer's receipt.
      • Genesis: the ledger's first entry: who may measure, who may activate, and the policy, fixed before anything it weighs.
      • Measurer: a key the genesis names as allowed to sign values. Activator: a key the genesis names as allowed to sign the switch.
      • The switch: the one entry that would make an allocation live. Off until an activator signs it; these books hold none.
      • Sandbox allocation: the arithmetic of how a pool would divide by credit, computed by anyone, binding on nobody.
      • Re-derive: rebuild the books from their first entry, checking every signature, link and gate again, and arrive at the same final hash.

      Questions

      Are contribution units money?

      No. A contribution unit is an internal record of measured work: who did which work that others used and checked. Nothing here moves anything of value, and the code has no way to. Whether an allocation is ever worth anything is the ledger owner's decision, with legal advice, outside this code.

      What is the switch?

      A signed record that only an activator named when the ledger began can make. Until it exists, the ledger refuses any live allocation; anyone can compute a sandbox allocation, marked as such. These books hold no switch: the switch is off.

      Can someone credit themselves?

      Not here. A value is recorded only from a measurer the ledger names, only on a job it has not recorded before, and the auditor's books take it only after finding the signed answer it was for, from the node that gave it, and checking that answer's receipt. A value one unit off what was measured is refused.

      What did not hold?

      The network path's claim said a merge with a larger network would refuse exactly one entry, the one release that clashed. It refused that release and every value that would have followed it to the key that had taken the living site's name first, eleven in all, and so the living site had no part in the network's allocation. That is the right outcome for the books and the claim is kept as failed: the lesson is that a node's name must be tied to its key before it joins a larger network. That is now done and measured, as a fix with claims of its own. A second claim held the source of every module to the same list of words as the page: the page itself is clean, but the code names break-it's cost reader as break-it named it and two test files use the words as test data, so it failed too and is kept.

      Can someone take a node's name?

      Not any more. A node's name is node: and the first 16 hex digits of its key, and one rule now holds at every door: a node is recorded only under its own key's name. Nine attempts to take one were sealed before the fix was written, and every one is refused. The books also refuse to merge into a network that does not hold the rule. Taking a name would now mean finding another key whose first 64 bits match, a search of about 2 to the 64 keys.
